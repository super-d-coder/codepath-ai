# codepath-ai 项目规范与架构约束

> 本文档是给后续开发 Agent 的项目交接说明。目标是让新 Agent 先理解项目，再开始修改代码，避免重复分析和擅自改变架构。

- `doc/02-InfoFlow-MVP开发计划.md` 是 InfoFlow 的范围与设计基线，不用它覆盖实际开发事实；
- `doc/infoflow/01-InfoFlow-MVP开发情况.md` 记录 InfoFlow 的已实现内容、配置、验证记录和待验收项；

## 3. DDD 与六边形架构约束

### 3.1 领域层职责

领域层路径：

```text
codepath-ai-domain/src/main/java/com/superd/domain/
```

现有领域上下文包括：

```text
agent/     # Agent 装配、聊天和工作流
ssh/       # SSH 连接领域
business/  # 预留业务领域
```

新增 InfoFlow 时，应作为新的领域上下文：

```text
com.superd.domain.infoflow
```

领域层可以包含：

- Entity：领域实体
- Value Object：值对象、枚举、结果对象
- Aggregate：聚合根（只有确实需要时再创建）
- Service：领域服务
- Adapter Port：出站端口接口
- Adapter Repository：仓储接口

领域层不能直接依赖：

- MyBatis DAO
- MyBatis PO
- HTTP 客户端具体实现
- GitHub/Hacker News SDK
- Controller
- Infrastructure 实现类

### 3.2 Port / Adapter 规则

项目已有明确约定：

```text
Domain 定义接口
    ↓
Infrastructure 实现接口
```

例如 SSH：

```text
领域端口：
com.superd.domain.ssh.adapter.port.ISshSessionPort

领域仓储：
com.superd.domain.ssh.adapter.repository.ISshConnectionRepository

基础设施实现：
com.superd.infrastructure.adapter.repository.ssh.SshConnectionRepository
```

因此 InfoFlow 必须遵循：

```text
com.superd.domain.infoflow.adapter.port.*
com.superd.domain.infoflow.adapter.repository.*

com.superd.infrastructure.adapter.port.*
com.superd.infrastructure.adapter.repository.*
```

不要把 HTTP、MyBatis、JSON 解析实现放到 domain。

### 3.3 领域服务规则

现有领域服务采用接口 + Spring 实现类形式：

```java
public interface ISshConnectionDomainService {
    // 领域用例
}
```

```java
@Slf4j
@Service
public class SshConnectionService implements ISshConnectionDomainService {
    private final ISshConnectionRepository repository;

    public SshConnectionService(ISshConnectionRepository repository) {
        this.repository = repository;
    }
}
```

InfoFlow 领域服务应负责：

- 编排采集端口和仓储接口；
- 处理采集结果；
- 定义业务默认值；
- 处理领域级校验；
- 不直接操作 HTTP 和 SQL。

## 5. Lombok 与注入规范

现有代码大量使用：

```java
@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
```

实体和 PO 可以沿用上述组合。

现有代码同时存在 `@Resource` 和构造器注入。新代码优先使用构造器注入，原因是：

- 依赖明确；
- 更容易单元测试；
- 避免字段可变依赖。

如果为了和同一模块的代码保持一致使用 `@Resource`，必须保持风格统一，不要同一个类混用两种方式。

## 6. Infrastructure 规范

### 6.1 DAO

DAO 使用 MyBatis 注解：

```java
@Mapper
public interface ISshConnectionDAO {
    void insert(SshConnectionPO po);
    SshConnectionPO queryByConnectionId(@Param("connectionId") String connectionId);
}
```

约束：

- DAO 只面向 PO；
- DAO 不返回 Domain Entity；
- 参数需要命名时使用 `@Param`；
- SQL 放在 `codepath-ai-app/src/main/resources/mybatis/mapper/` 下的 XML 中；
- XML namespace 必须等于 DAO 全限定类名。

### 6.2 PO

PO 只代表数据库记录：

```java
@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class SshConnectionPO {
    private Long id;
    private LocalDateTime createdAt;
}
```

不要把 PO 当成接口 DTO，也不要让 PO 泄漏到 Controller。

### 6.3 Repository Adapter

Repository 负责：

```text
Domain Entity ↔ PO ↔ DAO
```

现有 SSH Repository 的模式：

```java
@Repository
public class SshConnectionRepository implements ISshConnectionRepository {

    private final ISshConnectionDAO dao;

    @Override
    public SshConnectionEntity queryConnectionById(String id) {
        SshConnectionPO po = dao.queryByConnectionId(id);
        return po == null ? null : toEntity(po);
    }
}
```

InfoFlow 不能让 Domain Service 直接调用 DAO。

## 7. MyBatis 规范

Mapper XML 示例位置：

```text
codepath-ai-app/src/main/resources/mybatis/mapper/ssh_connection_mapper.xml
```

InfoFlow XML 建议：

```text
infoflow_hot_repo_mapper.xml
infoflow_news_item_mapper.xml
```

XML 必须包含：

- 正确的 XML 声明；
- 正确的 MyBatis mapper DOCTYPE；
- 与 DAO 全限定类名一致的 namespace；
- resultMap；
- 明确列名，不使用 `SELECT *`；
- 软删除字段如存在，查询必须过滤；
- 唯一键冲突必须使用明确的 upsert 或 ignore 策略。

## 8. Trigger 层规范

现有 Controller：

```java
@RestController
@RequestMapping("/api/v1/")
@CrossOrigin(origins = "*")
public class AgentServiceController implements IAgentService {
}
```

统一响应体：

```java
Response<T>
```

Response 字段：

```java
private String code;
private String info;
private T data;
```

成功和失败响应应使用：

```java
ResponseCode.SUCCESS
ResponseCode.UN_ERROR
```

InfoFlow Controller 应沿用 `/api/v1/` 前缀和 `Response<T>`，不要另造响应格式。

## 9. SQL 与数据库规范

已有项目使用 MySQL/MyBatis。SQL 文件放在：

```text
codepath-ai/doc/sql/
```

InfoFlow SQL 文件建议：

```text
codepath-ai/doc/sql/infoflow.sql
```

MVP 至少需要：

- `infoflow_hot_repo`
- `infoflow_news_item`

去重必须通过数据库显式字段实现，不能写不可执行的函数索引设计。例如不要直接写：

```sql
UNIQUE(repo_name, DATE(collected_at))
```

应增加：

```sql
collected_date DATE NOT NULL
UNIQUE KEY uk_repo_date(repo_full_name, collected_date)
```

## 10. Agent / Armory 现状约束

主项目已有 Agent 装配链：

```text
YAML
  ↓
AiApiNode
  ↓
ChatModelNode
  ↓
AgentNode
  ↓
AgentWorkflowNode
  ↓
Sequential / Parallel / Loop
  ↓
RunnerNode
  ↓
InMemoryRunner 注册到 Spring
```

当前系统已经具备：

- YAML 驱动 Agent 配置；
- OpenAI 兼容 API 配置；
- Spring AI ChatModel；
- MCP Tool 装配；
- Skills 装配；
- Google ADK `LlmAgent`；
- Sequential、Parallel、Loop 工作流。

但 InfoFlow MVP **暂时不能接入 Agent、MCP、LLM、Memory**。本阶段只负责稳定的数据采集和查询基础设施。

后续接入 Agent 时，优先把 InfoFlow 领域能力封装为 Tool，而不是重写一套 LLM 调用链。

## 11. 当前不应做的事情

后续 Agent 开发时不要擅自：

- 新建独立 Python 服务；
- 新建 InfoFlow Maven Module；
- 修改 Armory 核心装配链；
- 引入 LangChain/LangGraph 实现 MVP；
- 引入 Redis、Kafka、Elasticsearch；
- 加入记忆系统；
- 加入用户登录、用户画像；
- 先开发前端再验证后端；
- 使用 GitHub Trending HTML 爬虫作为第一版唯一方案；
- 把第三方 API 调用写入 Domain。
